## S06 전체 기동과 실제 Vue 관측

새 컴퓨터에서 시작한다면 [다른 컴퓨터 실행·개발 안내](<../../가상 제조공장 실시간 통합 관제 시스템 - 다른 컴퓨터 실행·개발 안내.md>)를 먼저 따릅니다. Docker 준비·환경 파일 생성·Python 3.12 설정부터 설명하며, 기존 데이터가 있는 pull 환경의 절차도 구분합니다.

```sh
scripts/dev-stack.sh env       # 처음 한 번만. 기존 .env를 덮어쓰지 않음
scripts/dev-stack.sh up
scripts/dev-stack.sh status
# 사용 후 DB 파일을 보존하며 종료
scripts/dev-stack.sh down
```

기동된 [Vue 관측 앱](http://127.0.0.1:5173)에서 실제 실행을 선택합니다. 새 차체를 시연하려면 다음 명령을 실행하고 출력된 runId를 선택하세요. 일반 기동은 자동 생산하지 않습니다.

```sh
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --connected-demo
```

[실제 LIVE 화면](../../services/factory-console/preview-s06-live.jpg) · [소스 중단](../../services/factory-console/preview-s06-source-stopped.jpg) · [GOOD/PASS 태그 창](../../services/factory-console/preview-s06-tag.jpg) 캡처가 있습니다. `factory-gui/`는 초기 디자인 시안이고, 실제 화면은 `services/factory-console/`입니다.

Docker Desktop이 없는 macOS에서는 `scripts/local-docker.sh start/stop`으로 로컬 Lima 엔진을 쓸 수 있습니다. 자세한 내용은 [전체 실행 안내](../../infrastructure/README.md)에 있습니다.

## S02-02 셀 작업·검사 확인

```sh
scripts/simulator.sh run --demo-work
```

서버 없이 차체 한 대의 ASM-01 → ASM-02 → QC-01 작업 기록과 PASS 결과를 출력합니다. 작업 시간은 4/6/3초이며 결과 차체는 QC 셀에 남습니다. 이 명령의 공정 간 이동은 **시험 배치**이며 배차/예약 규칙은 별도 --demo-dispatch로 확인합니다. 모델의 AGV 운송은 아래 --demo-transport로 확인합니다. 이 오프라인 명령은 GUI 데이터 공급부가 아닙니다. 실제 연결은 S06의 --connected-demo를 사용합니다. [작업 11 설명](<../work-notes/작업 11. 셀 작업과 최종 검사.md>)을 참고합니다.

## S02-03 슬롯 예약·배차 확인

```sh
scripts/simulator.sh run --demo-dispatch
```

서버 없이 만석인 목적지로의 배출 승인 거절, 빈 슬롯 확보 후 차체를 셀에 보유한 배차, 마지막 슬롯의 두 요청 중 하나만 승인을 확인합니다. 기본 C=3/W=2/R=1/A=0이며 R에는 픽업 전 예약도 포함합니다. 승인된 AGV는 TO_PICKUP이고 이 배차 확인 명령에서는 픽업/운송을 진행하지 않습니다. 모델 운송은 --demo-transport로 확인합니다. [작업 12 설명](<../work-notes/작업 12. 슬롯 예약과 AGV 배차.md>)에 원리와 최소 검증을 기록했습니다.

## S03 수집 저장과 명시적 송신

기동한 수집기의 TCP 주소는 127.0.0.1:9090입니다. 원본 NDJSON 파일은 다음 명령으로 한 사건씩 저장 확인합니다.

```sh
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --send-events /absolute/path/events.ndjson
# 필요한 저장/통신 경계 확인: 별도의 PostgreSQL 17.11 검증 클러스터
python3 scripts/verify-databases.py --suite ingestion
# 이미 실행 중인 Compose에서 새 run 1대 송신과 DB 원본 확인, 자기 run만 정리
python3 scripts/verify-ingestion-source.py
```

성공 ACK는 수집 DB가 원본/전달 책임을 맡았다는 뜻입니다. 아직 관제 업무 반영이나 GUI LIVE를 뜻하지 않습니다. Python 미확인 목록은 메모리이며 프로세스 종료 후 상태 복원은 P0 범위 밖입니다. [수집 실행 안내](../../services/ingestion-service/README.md) · [Python 실행 안내](../../services/factory-simulator/README.md).

## S04 관제 업무와 조회

```sh
python3 scripts/verify-databases.py --suite operations
python3 scripts/verify-operations.py
```

첫 명령은 별도 임시 PostgreSQL에서 S04의 핵심 경계 7개만 확인합니다. 두 번째는 기동한 Compose에 새 UUID run의 모델 사건 60건을 명시적으로 HTTP 반영하고, DB 원본/태그 HOLD/품질/알람을 확인한 뒤 자기 run만 정리합니다. 검증 UUID의 기존 행이 있으면 쓰기와 정리를 거절합니다. 자동 outbox 전달이나 전체 GUI 연결 증거로 설명하지 않습니다. [관제 안내](../../services/operations-service/README.md)와 작업19~22를 참고합니다.

## S05 자동 전달·복구·진단

- [S05-01 / 작업23](<../work-notes/작업 23. S05-01 영속 outbox와 자동 HTTP 전달.md>): 발송 장부·HTTP worker·시도 제한과 완료/커서 동시 저장.

- [S05-03 / 작업25](<../work-notes/작업 25. S05-03 재시작 복구와 전달 진단·재개.md>): DB 재개·현재 연결/대기 진단·이유를 남기는 명시적 재개.
- [수집 실행/진단 안내](../../services/ingestion-service/README.md) · [검증 기록](<../validation/최소 검증 시나리오와 도구.md>).

```sh
# 수집 코드만 반영, 기존 DB/볼륨 보존
scripts/dev-stack.sh compose up -d --build --wait --no-deps ingestion-service
# 필요한 경계만, 새 PostgreSQL 두 DB와 실제 관제 HTTP: Java8개
python3 scripts/verify-databases.py --suite delivery
# 기존 Compose에서 새 run의 정상60건 자동 전달/REST 확인
python3 scripts/verify-delivery.py
# 별도 개발 환경에서 서비스 중단/재시작까지 한 번에 확인
python3 scripts/verify-delivery.py --with-restarts
```

TCP ACK는 수집 저장 확인이고, 관제 반영은 그 뒤의 별도 결과입니다. 관제 서비스가 멈춘 동안에도 이후 보고는 저장되고, 수집 서비스를 재시작해도 전달 대기·커서·시도 횟수가 유지되는지 확인합니다. 복구 뒤에는 원본 60건의 바이트·해시 일치, 전달 대기 0, REST 상태가 LIVE에서 FINISHED로 바뀌는 것을 확인합니다.

## S08 장애·복구와 100대 통합 검증

S08-01~04에서 별도 PostgreSQL과 두 서버로 다음을 확인합니다: 예약 취소·반환, 목적 셀 정지 중 도착과 복구, TCP ACK 유실·재전송, 12초 보고 단절, 두 서비스와 각 DB·PostgreSQL 재시작. 5대 실행 원본 216건과 100대 실행 원본 3,533건이 두 DB에서 순번·바이트·해시까지 일치했습니다. 100대 실행에서는 2,764 tick 동안 차체 단일 위치와 용량 규칙을 확인하고, 중간 전체 스냅샷 28개와 최종 상태를 관제 API와 비교했습니다. 작업 300 · 검사 100 · 운송 400건, PASS 80 / FAIL 20, 검사·운송 원본 각 10회 재전송 시 실적 증가 0, 실행(run) 간 격리를 확인했습니다. 자세한 결과는 [S08 장애·복구 통합 검증](<S08 장애·복구 통합 검증.md>)에 있습니다.
