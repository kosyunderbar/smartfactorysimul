# 요구사항과 공정 규칙

이 프로젝트를 시작할 때 정한 요구사항과 공장 모델의 규칙입니다. 코드와 화면은 이 규칙을 기준으로 만들고 검증했습니다.

## 1. 해결하려는 문제

| 문제 | 설정한 상황 | 관제가 보여줄 것 |
|---|---|---|
| 목적지 수용량 오판 | 지금 대기 중인 차체만 세고, 이동 중인 차체는 빼고 셈 | 대기 + 예약으로 만석을 판단하고, 배출이 막힌 이유를 표시 |
| 차체 추적의 어려움 | 차체가 셀과 차량을 바꿔 가며 이동 | 가상 태그로 차체의 위치·공정·검사·운송 이력을 연결 |
| 오래된 데이터 오판 | 마지막 정상 상태가 지금 상태처럼 보임 | 마지막 보고 시각과 데이터 신선도를 함께 표시 |
| 중복 보고로 인한 실적 왜곡 | 같은 검사 결과가 다시 전송됨 | 사건·검사 식별자로 한 번만 반영 |

## 2. 공장 모델

실제 설비 대신 Python으로 만든 학습용 모델입니다. 산업 프로토콜과 실제 장비는 연결하지 않았습니다.

| 구성 | ID | 역할 |
|---|---|---|
| 차체 투입 구역 | BODY-IN | 새 차체와 가상 태그 생성 |
| 조립 셀 2개 | ASM-01, ASM-02 | 조립 작업 (작업 위치 1면) |
| 검사 셀 1개 | QC-01 | 차체별 PASS/FAIL 판정 |
| 셀별 대기 공간 | BAY-ASM-01, BAY-ASM-02, BAY-QC-01 | 차체가 셀에 들어가기 전 대기하는 공간 (기본 3면) |
| 차체 운반 AGV 2대 | AGV-001, AGV-002 | 1대당 차체 1대 운반 |
| 부품 공급 AMR 1대 | AMR-001 | 부품 창고와 조립 셀 사이 부품 키트 운반 (차체 대기 공간은 쓰지 않음) |
| 결과 구역 | GOOD, HOLD | 검사 PASS / FAIL 차체 분리 |

공정 순서: `BODY-IN → ASM-01 → ASM-02 → QC-01 → GOOD / HOLD`

모든 구간은 AGV가 운반합니다. 셀로 이동할 때는 목적지 셀의 대기 공간(Bay) 슬롯을 예약하고 그곳에 도착한 뒤(R→W), 셀이 비어 있으면 곧바로 셀에 들어가며 슬롯을 반환합니다(W−1). 셀에서 셀로 바로 넘기는 경로는 없습니다.

## 3. 핵심 규칙: 대기 + 예약으로 만석 판단

```text
C = 대기 공간의 전체 슬롯 수
W = 지금 대기 공간에 실제로 있는 차체 수
R = 그 대기 공간으로 가기로 예약된 운송 수 (픽업 전·이동 중 포함)
A = C − W − R  (남은 슬롯)

W + R ≥ C  →  새 예약·배출 금지
W + R < C 이고 빈 AGV가 있음  →  슬롯 1면 예약 후 배출
```

눈에 보이는 빈자리만 세면, 이동 중인 여러 AGV가 같은 자리를 기대할 수 있습니다. 그래서 출발 전에 목적지 슬롯을 먼저 예약하고, 예약도 사용 중인 자리로 셉니다.

| 상황 | W | R | C | A | 새 배출 |
|---|---:|---:|---:|---:|---|
| 2대 대기, 도착 예정 없음 | 2 | 0 | 3 | 1 | 허용 |
| 마지막 1면 예약 | 2 | 1 | 3 | 0 | 금지 |
| 예약 차량 도착 | 3 | 0 | 3 | 0 | 계속 금지 |
| 대기 차체 1대가 셀로 들어감 | 2 | 0 | 3 | 1 | 다시 허용 |

- 이미 예약한 차량의 도착은 막지 않습니다. 만석이라고 예약 차량까지 멈추면 그 예약을 쓸 수 없어 모델이 스스로 멈춥니다.
- `0 ≤ W + R ≤ C`를 벗어나면 정상 상황이 아니라 모델 오류로 보고 실행을 멈춥니다.

## 4. 예약의 흐름

| 단계 | 함께 바뀌는 것 | 차체 위치 |
|---|---|---|
| 운송 할당 | 빈 AGV 선택 + 목적지 슬롯 예약 (R+1) | 출발지 |
| 픽업 | 출발지에서 차체를 꺼내 AGV에 적재 | AGV |
| 이동 중 | 예약 유지 (중간에 해제하지 않음) | AGV |
| 대기 공간 도착 | 예약 → 대기 (R−1, W+1) | 대기 공간 |
| 셀 진입 | 슬롯 반환 (W−1) | 셀 |
| 출발 전 취소 | 예약과 차량 할당 해제 | 출발지 |

취소는 픽업 전에만 할 수 있습니다. 차체가 AGV에 실린 뒤에는 취소하지 않습니다.

## 5. 상태를 바꾸는 주체

- **배차·예약·위치 같은 물리 상태는 Python 공장 모델만 바꿉니다.** 수집·관제 서버와 화면은 받은 보고를 검증·저장·표시만 하고, 직접 배차하지 않습니다.
- 통신이 끊기거나 서버가 재시작돼도 예약을 자동으로 풀지 않습니다.
- 차체는 투입 구역, 셀, 대기 공간, AGV, 결과 구역 중 정확히 한 곳에만 있습니다. 예약은 위치가 아닙니다.

## 6. 셀 상태와 화면 표시

| 셀 상태 | 의미 |
|---|---|
| 대기 | 작업 위치가 비어 다음 차체를 기다림 |
| 작업 중 | 차체를 작업·검사 중 |
| 배출 대기 | 작업을 마쳤지만 내보내지 못함 |
| 설비 정지 | 셀 이상으로 정지 (차체와 남은 작업 시간은 유지) |

배출 대기의 이유는 **목적지 슬롯 만석**, **빈 AGV 대기**, **픽업 차량 대기**로 나눠 표시합니다.

알람은 심각(설비 정지, 소스 연결 끊김, 업무 반영 중단)과 주의(Bay 만석, 보고 지연)로 나눠 표시합니다. 빈 AGV 대기처럼 정상적인 흐름 대기는 알람을 만들지 않습니다. 알람 확인 버튼은 확인 기록만 남기고, 설비 복구나 슬롯 반환을 대신하지 않습니다.

## 7. 데이터 전달 요구사항

- 수집 서버는 원본을 저장하고 커밋을 마친 뒤에만 수신 확인(ACK)을 보냅니다.
- 관제 서버가 멈춰도 아직 전달하지 못한 원본은 수집 쪽에 남아 있다가, 복구 후 다시 전달합니다.
- 같은 보고가 다시 와도 검사·운송 실적은 한 번만 집계합니다.
- 최신 보고가 일정 시간 오지 않으면 마지막 값을 현재 상태처럼 보여주지 않고, 마지막 보고 시각과 함께 표시합니다.
